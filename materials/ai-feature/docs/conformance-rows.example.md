# Приклад рядків docs/conformance.md для зрізу 4

Рядки додавайте у ВАШУ таблицю `docs/conformance.md` (цей файл у репо не копіюйте). AC ID — ID критеріїв PM;
`AC-DRAFT-01` — лише заглушка з наборів цього репо.

Після злитого PR «Специфікація» (AC уже в `openspec/specs/`, реалізації ще немає):

```markdown
| AC-DRAFT-01 | 10 golden cases PM: поля чернетки збігаються з очікуваними | — | — | відкладено (чекає реалізації) |
```

У PR «Реалізація», де з'являються код і тест:

```markdown
| AC-DRAFT-01 | 10 golden cases PM: поля чернетки збігаються з очікуваними (офлайн-реплей записаних відповідей) | `src/lib/ai/draft.ts` (proposeDraft), `src/lib/ai/schema.ts` | `tests/golden.test.ts` | реалізовано |
```

Що перевіряє `npm run ac:coverage` у цьому рядку:

- шляхи в бектиках із колонок «Код» і «Тест» існують (інакше WRONG-REF);
- у файлі з колонки «Тест» є непропущений тест, назва якого ПОЧИНАЄТЬСЯ з `AC-DRAFT-01` — у наборі це
  `it.each(cases)("AC-DRAFT-01: golden $id", …)` (інакше MISSING або WRONG-REF);
- AC є у вашій специфікації `openspec/specs/**` (інакше тест — ORPHAN, і job `conformance` червоний).
  Тому тест з AC ID у назві додавайте лише після злитого PR «Специфікація» з цим AC.

Живий прогін (`npm run eval`) — не тест для `ac:coverage`: він не в `*.test.ts` і без ключа пропускається.
Його звіт (`evals/reports/<дата>.md`) — доказ якості моделі для PM і для домашки, а не рядок матриці.
